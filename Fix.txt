Wo ich den Fix setzen würde

Die Logik, die eine bestehende Kleinanzeigen-Such-URL für Seite N verändert, sollte nicht den Suchbegriff bzw. den Subcategory-/Query-Slug entfernen.

Aus:

/s-kueche-esszimmer/liebherr/k0c86

muss werden:

/s-kueche-esszimmer/seite:2/liebherr/k0c86

bzw.:

/s-kueche-esszimmer/seite:6/liebherr/k0c86

Wichtig

Ich würde nicht einfach einen Sonderfall

if category_id and query:
    ...

einbauen.

Besser ist eine generische Pagination-Funktion:

original search URL
        │
        ▼
/s-kueche-esszimmer/liebherr/k0c86
        │
        │ insert page marker
        ▼
/s-kueche-esszimmer/seite:6/liebherr/k0c86

Dabei sollte die vorhandene URL-Struktur möglichst vollständig erhalten bleiben.
Wahrscheinlicher Fehler

Ich vermute eine Logik in der Art:

parts = url.split("/")

und anschließend wird anhand der Kategorie-/Pfadbestandteile eine neue URL zusammengesetzt.

Oder eine Funktion arbeitet sinngemäß so:

page_url = f"{base_url}/seite:{page}/{category_suffix}"

wobei base_url bereits auf

/s-kueche-esszimmer

gekürzt wurde und dabei liebherr verloren geht.

Das würde exakt dein Verhalten erklären.
Robuster Fix

Falls die Pagination aktuell Regex-basiert ist, würde ich sie stattdessen direkt auf dem bestehenden URL-Pfad durchführen.

Für eine URL wie:

https://www.kleinanzeigen.de/s-kueche-esszimmer/liebherr/k0c86

sollte die Funktion erkennen:

/s-kueche-esszimmer/
    liebherr/
    k0c86

und seite:N nach dem Kategoriepfad, aber vor Suchterm und k0c86 einfügen:

/s-kueche-esszimmer/seite:N/liebherr/k0c86

Für die anderen möglichen Strukturen muss das natürlich ebenfalls gelten.
Noch besser: Pagination aus der echten Next-URL ableiten

Wenn Kleinanzeigen auf Seite 1 einen Link zur nächsten Seite liefert, würde ich diesen Link bevorzugen, statt die URL selbst zusammenzubauen.

Also etwa:

next_page_url = await page.locator(
    'a[rel="next"]'
).get_attribute("href")

oder anhand des tatsächlich vorhandenen Pagination-Elements.

Dann muss dein Scraper nicht wissen, ob Kleinanzeigen die URL als

/s-kueche-esszimmer/seite:6/liebherr/k0c86

oder irgendwann anders strukturiert.

Das wäre langfristig wesentlich stabiler.

Mein konkreter Fix-Vorschlag

Ich würde die Pagination-Funktion so ändern, dass sie für deinen Fall garantiert:

Seite 1:
https://www.kleinanzeigen.de/s-kueche-esszimmer/liebherr/k0c86

Seite 2:
https://www.kleinanzeigen.de/s-kueche-esszimmer/seite:2/liebherr/k0c86

Seite 3:
https://www.kleinanzeigen.de/s-kueche-esszimmer/seite:3/liebherr/k0c86

...

Seite 6:
https://www.kleinanzeigen.de/s-kueche-esszimmer/seite:6/liebherr/k0c86

...

Seite 12:
https://www.kleinanzeigen.de/s-kueche-esszimmer/seite:12/liebherr/k0c86

und dabei query, Kategorie, k0c86 sowie alle URL-basierten Filter unverändert erhalten.

Die vorhandene API-Dokumentation bestätigt auch, dass die URL-basierte Variante genau dafür gedacht ist: Eine vollständige Kleinanzeigen-Such-URL wird übernommen und die Seitennummern werden für die weiteren Abrufe injiziert. GGitHub
Wichtigster Befund

    Der Bug sitzt sehr wahrscheinlich in der Funktion, die aus der ursprünglichen Search-URL die URL für page > 1 erzeugt. query/Slug liebherr wird beim Einfügen von seite:N verworfen.
